# Field test checklist – LMU Championship race, 2026-11-22

Versioned, fill-in checklist for the first full race with the current `dev` build. It is a test protocol, not a
specification: expected behaviour below is what the documented implementation should do (see
[ARCHITECTURE.md](../ARCHITECTURE.md), [RESOURCE_STRATEGY.md](../RESOURCE_STRATEGY.md),
[TRACKMAP_RACE_CONTROL.md](../TRACKMAP_RACE_CONTROL.md)). Nothing here claims a feature is verified until a row is marked PASS.
Multi-agent scenarios are **not** part of this test; see [future-multi-agent-plan.md](future-multi-agent-plan.md).

## Privacy: public checklist, local protocol

This file is a **generic** checklist and is meant to stay free of real data. Roles are used instead of names.

* The **filled-in copy and all evidence** (real session IDs, driver slugs and names, agent IDs, screenshots, timestamps, stream
  recordings, server revision details tied to a person) are kept **only locally**, outside Git, for example under the ignored
  `data/field-tests/` folder (for example `data/field-tests/2026-11-22-protocol.md`). Do not commit, attach or paste them.
* Raw captures and their metadata stay local (section 8). Public regression tests use synthetic data only.
* What goes to GitHub issues: results reduced to the technical problem and anonymised (`Driver A`, `Remote Engineer`, `Operator`),
  without session IDs, slugs, agent IDs, infrastructure details, identifying screenshots, or counts/timings from which a person's
  activity can be reconstructed.
* Self-check before posting anything: no names or handles, no IDs or addresses, no screenshots that show names or the address bar,
  no exact times of a specific person's race participation, nothing that identifies who was or was not connected.

Copy this file for the run (or print it) and fill the copy **locally**; do not commit or attach the filled copy (see Privacy below).

## 1. Scenario and roles

| Role | Who | Where | Provides / uses |
| --- | --- | --- | --- |
| **Driver** | the single driver | Gaming PC with LMU, Pitwall and **the only** Stintara agent; Chromebook (Lenovo IdeaPad Duet) as in-race screen | Drives the Championship race alone at 12:00. All Stintara telemetry (fuel, VE, tyres, strategy) comes from this one agent |
| **Remote Engineer** | a second person | Own computer, browser only | No LMU DLC, not in the race, cannot join as engineer, **no agent, no telemetry**. Watches the YouTube stream, public Stintara and LMU Pitwall in a browser |
| **Technical follow-up** | Operator | After the race | Verifies persistence, data quality and issue assignment read-only |

**Key question of this test:** can a remote engineer without own LMU telemetry derive a sensible strategy assessment from
Stintara (plus stream and Pitwall) alone? Answer it in Part B.6 and in the evaluation sheet (Part F).

### Result and severity vocabulary

* **Result:** `PASS`, `FAIL`, `N/A` (not applicable or not reached; say why in Notes). Leave blank until tested.
* **Critical (C):** wrong data presented as right: wrong driver/participant, a wrong or negative gap/interval, fuel/VE or pit
  instruction that contradicts the game, a duplicated or lost session, an agent/page crash or unusable page.
* **UX:** correct data, but not found, not understood or hard to operate (touch, size, wording, scrolling).
* **LIM (known limitation):** expected behaviour of the telemetry or of the current implementation (section 2). Record it, do not
  count it as a defect, unless it behaves worse than described.
* The column *If FAIL* says which class a failure of that row normally belongs to; judge each case.

### Time base and YouTube latency (read before comparing anything)

The YouTube stream is typically 10–40 s behind real time. Pitwall in a browser and Stintara are fed from the same game
and are close to real time (Stintara polls about every 0.5 s; vehicle dots about every 0.25 s).
**Never classify a difference between the stream and Stintara as a fault without a time alignment.**

1. At the race start (green flag) the Remote Engineer notes the stream time shown for the first green frame and the session clock Stintara shows at
   that moment; the difference is the **stream offset** (`Δ`). Repeat after the first pit stop and at the end; write all values in
   the run header.
2. Compare events by the **in-game session clock / lap number**, not by wall-clock time. Stream moment = Stintara moment + `Δ`.
3. Stintara vs **Pitwall (browser)** needs no latency correction beyond about 1–2 s.
4. A mismatch only counts if it persists after applying `Δ` (and, for gaps, after the lap/pit context in section 2).

### 2a. Offline validation of lapped intervals (#68, #10) – what is already known

Replay of the current interval measurement (`interval_history`, as merged) over three private real race captures: two usable ones
(a single-class GT3 race and a multi-class race) and one short race with too few moving lapped cars. Aggregate numbers only; no
event, driver or session is identifiable from them, and the captures stay local. Offline replay uses the production normaliser and measurement code on recorded scoring frames.

| Case | Offline result | Consequence for Sunday |
| --- | --- | --- |
| Two cars with the **same lap deficit** (≥ 1 lap), adjacent positions | A measured interval exists for about 70–78 % of such pair-samples in the two usable captures; the rest is withheld by the 60 s pit guard (about 21–29 %) or by missing history (about 1 %) | Expect a value most of the time while both cars are on track, and `—` for about a minute after a pit stop of either car |
| Both cars on track, mid-race | Value present in roughly 70–100 % of those samples, rising over the race as history builds | A persistent `—` for two on-track lapped cars well after their stops is worth recording (B-13) |
| Values that are zero, negative or above 300 s | None in about 156,000 measured pair-samples | Any such value on Sunday is a Critical finding (B-11) |
| Plausibility: measured interval vs. distance gap divided by the follower's recent speed | Median ratio about 1.0 (5th–95th percentile about 0.6–2.0) | Single samples can deviate when a car brakes or accelerates; judge trends and several samples, not one value |
| Multi-class field, cross-class neighbours | Measured like same-class pairs (about 73 % coverage, no anomalies) | Cross-class P−1/P+1 values are expected; note the class mix when comparing with Pitwall |
| Different lap deficits | No value, by design (phase 2 is not implemented) | `—`/reason text is expected (L1) |
| Lead-lap cars | Not part of this measurement; they use the leader-gap rule | Compare as in B-10/B-11 |
| Race start and first minutes | Little or no value while cars leave the pits and history builds | Do not count `—` at the start as a defect |
| One short race in which most lapped cars sat in the pits | Only a few dozen on-track lapped pair-samples, all with values | That capture cannot judge coverage; Sunday is the first full test with a moving lapped field of this size on this build |

Not covered offline and therefore the **priority live checks** for the Remote Engineer: the first lapped pair after the
start (how long until a value), the value after a pit stop returns after about a minute, restarts and full-course yellow, the
finish phase, rain, and any pair where the sign or size contradicts Pitwall or the stream after applying `Δ`.
